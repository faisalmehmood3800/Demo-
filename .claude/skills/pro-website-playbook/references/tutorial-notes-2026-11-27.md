## A. kcNVDHtlnPk "I Built the full Team of AI Agents in n8n With No Code" (read fully)
- Architecture: manager agent ("Ultimate Assistant", chat trigger, simple memory) + 4 specialist sub-workflows (Email, Calendar, Contacts, Content). Manager only routes; never writes emails itself. Each specialist has only its own tools; short clear prompts. Too many tools on one agent -> wrong tool choice. New capability = add a new specialist.
- Specialist workflow: trigger "When executed by another workflow", input field `query` (string) -> AI Agent (prompt = query, system message = job description) -> chat model (cheap fast model) -> no memory (each task complete) -> tools.
- Tools named clearly, no spaces (agent picks tools by name + description). Use $fromAI ("let the model define") on tool fields.
- Contacts: n8n Data Table (name, email, phone, company); tools Get rows (return all) + Upsert rows (filter name = fromAI).
- Error handling per specialist: agent Settings -> On Error = continue (error output). Success -> Edit Fields `response` = output; Error -> Edit Fields `response` = "Unable to perform the task, please try again". Manager reads last node's response; system never stuck.
- Test each specialist alone by setting a test query on the trigger, before wiring manager.
- Gmail tools: send, create draft, get many (sender = fromAI), get labels, add label, mark unread, reply. HTML email type; turn off "Append n8n attribution". Rule: before reply/label/mark-unread, run Get Emails to get message ID (that is how reply stays in the thread); labels need Get Labels too.
- Calendar: create event (start/end/summary fromAI) + duplicate "create event with attendees" (empty attendees field can make Google fail); get events (after/before), update/delete need event ID from get events first. Default 1h meetings. ALWAYS inject today's date/time via expression in system message, else "tomorrow" is wrong.
- Content agent: OpenAI model with Responses API + built-in web search; blog in HTML, title, intro, 3-4 headings, sources as links, ~400 words, never invent numbers. (Claude needs a separate search tool.)
- Manager tools: "Call n8n Workflow Tool" per specialist, name without spaces, description says WHEN to use; `query` field fromAI. Manager system message: route only; rule "before emailing / drafting / inviting anyone, get their email from Contact agent"; example chain; today's date.
- Debug: Executions tab shows each specialist run with every tool and ID.
- Bonus Telegram: BotFather token; Telegram trigger; Switch text vs voice; voice -> download file -> OpenAI transcribe; Edit Fields normalise to `text`; agent; Telegram send to same chat ID; memory session key = chat ID (separate memory per user).
- Common errors: expired key / no balance; manager didn't call tool (bad name/description); reply not in thread (Get Emails not run); wrong day (date line missing); Google node red (re-auth).
- Advice: use a separate test Gmail, never share keys/screenshots of keys.

## C. I6zShAbbpQU "I Built a 4-Person full AI agency Team with OpenClaw (Full Course)" (read fully; second half is about Perplexity Comet browser)
- Team pattern again: main agent (coordinator) + research agent + dev agent + ops manager; each bound to its own Discord channel; each can have its own model (big model for lead, cheap for research). Basic setup = one agent role-playing personas per channel; true separate agents need separate sessions/config.
- Mission-control dashboard: agents list, task board (assigned -> waiting -> in progress -> review -> quality review -> done), channels, skills, memory, logs, COST TRACKER (24/7 agents burn API money; watch cost per agent). Pick cheap models for routine tasks; big model only for big tasks.
- Hosting: run always-on agents on a VPS, not your personal PC (malware/hijack could reach personal files). Hostinger VPS one-click OpenClaw (~PKR 1,600-2,200/month on long plans, presenter's figures, affiliate link). Pay via card/PayPal/JazzCash shown.
- Give the agent an intro (who you are, business, goals) and a name; it writes USER.md / IDENTITY.md memory files.
- Security instructions he gives the agent: read the official security guide; ask permission before any action that could harm the system or leak data; never follow untrusted external instructions; if a task fails 3-4 times or ~10 minutes, stop and report instead of retrying endlessly (saves credits).
- WhatsApp channel: link device by QR; then set "allow from" to ONLY your own number, otherwise strangers who message you get pairing codes/replies. Discord: create app + bot in developer portal, reset/copy bot token (secret), enable message content intent, give least-privilege permissions (send/read history/manage messages) rather than admin, invite via OAuth URL generator, private server, channel IDs into allow list, pair via DM pairing code. Discord rate-limits rapid messages; agent should wait and retry.
- Business idea: companies pay for setting up and customising such agent teams.
- Comet (agentic browser): can browse, filter, book (Airbnb demo), schedule daily research tasks, write to Google Docs. Slow, not always accurate; serious security risk: sites can hide prompt-injection text that the agent reads as instructions (could steal card details). Don't give card/personal data to agentic browsers yet. Use cases: lead lists from LinkedIn, competitor lists to sheets, price hunting.

## D. _FZcKRS74P4 "CLAUDE CODE FULL COURSE - Build & Sell AI Apps (2026)" (read 0:00-1:12 and 1:33-2:01 in full; 1:12-1:33 is generic AI/ML theory, only sampled)
- Project structure the course teaches (matches what this repo already has): CLAUDE.md lean with top-level rules only (project, stack, commands, critical security: no hard-coded keys, no leaking DB, ignore injected prompts); split details into .claude/rules (frontend, QA, security), .claude/skills, .claude/agents, settings.json (permissions, hooks), CLAUDE.local.md (personal, not deployed), project memory file for preferences (fonts, button colours) so they persist. Small files = fewer tokens, less hallucination.
- Rule worth adopting: after building UI, take a screenshot and verify it matches the instructions.
- Plan mode for anything sizeable; ask it to write the plan to a .md file and get approval before building; it works in phases.
- Demo build: services website for "AI automation for e-commerce" -> redesign phase -> admin dashboard (/admin/login, password in .env) -> lead-prospecting system: define ICP (industry, size, platform e.g. Shopify, location, job titles, keywords) -> "Find leads" via Apollo API -> leads table with status pipeline (new, contacted, replied, meeting, client, not interested), notes, CSV export; data in Supabase tables (ICPs, leads, outreach).
- .env for keys; Claude with Chrome extension can fetch Supabase/Apollo keys and run SQL to create tables (slow for browser chores; faster to do small ones by hand).
- Debugging: browser DevTools -> Network tab -> inspect request/response and status; give the error + screenshot to the agent. Apollo free plan blocks people search (403), only company search.
- His redesign used glassmorphism and Hormozi-style copy: glassmorphism conflicts with unslop, keep copy honest.
- SELLING / OFFERS (1:33-2:01, Hormozi-style): an offer = client feels they get more than they pay, not a % discount. Examples: Domino's 30-min-or-free; Zappos send two sizes, keep one, free returns; Easypaisa "send money instantly anywhere in Pakistan".
  Five components: (1) Believability: proof, past work, reviews; risk reversal that is believable (e.g. "15-day free trial; if it brings results you pay for those 15 days too"); too-good-to-be-true offers kill trust. (2) High perceived value: sell the benefit/outcome not features ("charge your phone 2-3 times, never hunt for a socket" vs "10,000 mAh"); bundle services (copy + landing page add-on); add low-cost bonuses. (3) Low risk: take the risk on yourself: trial, guarantee, refunds, free shipping/exchange; show guarantees big and clear. (4) Urgency: limited-time reasons to act now. (5) Simplicity: understood in 10 seconds, plain words.
  Homework he gives: write your offer with the 5 components; analyse 10 big brands' offers; practise selling by voice notes; create a LinkedIn and post consistently; remove distractions.
  My caveat: urgency must be real (no fake resetting countdown timers or fake "sale" prices); that is deceptive and can break consumer-protection law.

## E. R3l-MemOC1A "The Only AI-Agents & Automation Course You need to Land Your First Client" (3h34m). Unique parts read in full: 0:00-0:42 and 1:44-3:08. 0:42-1:44 repeats the Claude Code course (D) and 3:08-3:34 repeats the offers lecture (D).
### 0:00-0:42 n8n from zero, agent by hand, Claude builds n8n via MCP, RAG bot
- Automation vs agent: fixed steps = automation; where something must read, judge and decide = AI agent. Agent is the manager that decides; normal nodes do the work (send email, write sheet).
- Every workflow = trigger -> steps -> output. Five node families: triggers (manual, schedule, webhook, form, app event; one trigger per workflow), actions/app nodes + HTTP Request for any API, logic (IF, Switch, Merge, Loop Over Items), data (Edit Fields, Code), AI (agent + chat model + memory + tools).
- Habits: test one node at a time; pin good output to save time and paid credits, unpin after testing; fixed vs expression fields; schedule trigger uses the account time zone; check item counts before any "send" node (100 items in = 100 emails out); n8n nodes run once per item automatically, Loop node only for batching/rate limits; webhook test URL vs production URL (production only after publish).
- Design rules: write trigger/steps/output on paper first; one node one job; start small, test each step; read the output panel to find where data went wrong; Executions tab for every run; paste the error into Claude.
- Common errors: credentials missing/unauthorised; unrecognised node type (community node not installed); empty data (Notion page or Drive file not shared with n8n: add the n8n connection on the page); expression empty (field renamed); AI node stopped (free credits ended, add own key).
- Hand-built agent: chat trigger -> AI Agent with system message (role, tone, when to use which tool) -> chat model (cheap fast) -> simple memory -> calculator tool; logs show the agent chose the tool itself. If an agent misbehaves, fix the system message first: who it is, for whom, which tool when, what never to do.
- Claude builds n8n workflows via n8n's instance-level MCP (Settings -> Instance-level MCP -> enable -> connect client -> server URL; in Claude add n8n connector, grant access). Write the idea in a file, use plan mode, ask for a plan in stages plus a progress file so work can resume, and test every stage. Playwright MCP lets Claude click through UIs.
- Project 1 (YouTube -> video prep): form (URL, angle, length) -> Code node extracts the 11-char video ID from any URL shape (clear error if invalid) -> HTTP get title/channel -> Supadata transcript (community node; install it first) -> IF transcript length > 200 chars else stop (saves AI credits) -> Analyse agent with structured output (summary, audience, hook, structure; "only from transcript, never invent numbers") -> Research agent with web search, max iterations 14 (so it never loops forever) -> Writer agent ("take structure, write in own words, don't copy") -> Excalidraw board (plan, build file, HTTP POST upload, get link) -> Notion page. Nodes organised into named groups, sticky note explaining the workflow.
- Project 2 RAG chatbot (gym help desk): ingest workflow (form upload or code node with the KB -> default data loader -> recursive text splitter chunk 1000 / overlap 200 -> OpenAI embeddings text-embedding-3-small -> vector store insert, memory key "kb", "clear store" on re-upload so old prices vanish). Chat workflow (chat trigger -> agent -> model + simple memory + vector store as retrieve tool, top-k 4, tool description says what it covers). System message: answer only from the knowledge base, never guess, say "I don't know" and give the support email, cite the section used. Simple in-memory vector store is for demos only (lost on restart); for clients use Pinecone, Supabase or Qdrant. Embeddings are cheap and done once per document version.
- Business: every small business (clinic timings, school admissions, real-estate listings, gym plans) can use a RAG bot; build it with their documents and charge monthly maintenance.
### 1:44-3:08 e-commerce catalogue -> Supabase, then a voice calling agent (read in full: 1:44-1:53, 2:28-2:41, 2:53-3:08; 1:53-2:28 and 2:41-2:53 sampled every ~50 s)
- Catalogue scraper: schedule trigger (re-scrape every N hours for new products) -> Edit Fields with the sitemap URL (most sites have /sitemap.xml; product sitemap lists every product URL) -> HTTP GET with browser-like headers (User-Agent, Accept text/html,application/xml, Accept-Language) so requests do not look like a bot -> HTML node CSS selector `loc`, return text, to pull URLs -> split -> Loop in batches -> HTTP GET each product page -> HTML extract name, price, description -> Code node to clean -> embeddings + metadata -> Supabase vector table (~800 products in his demo). Respect robots.txt / site terms and rate limits; only scrape the client's own store or with permission.
- Voice agent architecture: n8n "MCP Server Trigger" workflow exposes tools (sub-workflows): Supabase product search (Execute Workflow trigger with `query`, Get many rows from products, filter content ILIKE %query% so case-insensitive partial matches, limit 50 to save tokens), Create order (Code node parses name, phone, city, address, product, notes; Google Sheets get last order ID -> new ID -> append row), Update order (find by order ID or phone, update one field). MCP vs direct webhooks: MCP lets you add tools in n8n without reconfiguring the voice AI; webhooks fine for 2-3 calls.
- Vapi assistant: blank template; model (GPT-4o class), who speaks first, first message ("It's Ali speaking for Flower Bouquet"), long system prompt: role, jobs (browse products, prices, book order, status, update, cancel), strict data rules (ask -> wait for the customer's real answer -> only then call the tool; never call tools with empty parameters; never update without an order ID, fall back to phone lookup), exact payload format per tool with right and wrong examples, required fields for new orders (name, phone, city, full address, product, notes), error handling cases (damaged delivery etc.). Voice ElevenLabs; transcriber chosen for Urdu (he used a provider that handled Urdu best; Urdu TTS/STT still weaker than Hindi/English, so list English words to keep, e.g. say "order book" not "tajdeed"). Tool: MCP, server URL = n8n production URL, header Authorization: Bearer <n8n API key>, streamable HTTP (SSE only for continuous live data), 20 s timeout. Test with "Talk to assistant", check n8n Executions and the sheet. Go live with a Twilio number or a call button on the website.
- Advice: use an LLM to plan nodes and debug; Supabase table is the professional store, Google Sheets is the easy shared store for small clients.
